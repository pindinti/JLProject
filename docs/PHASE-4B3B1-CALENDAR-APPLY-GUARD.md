# Phase 4B.3b.1 — Calendar apply dependency guard

**Status** — Backend and migration draft prepared. Dependency routes remain closed and migration execution requires separate approval.

## Enforcement

Migration `0039` guards `apply_calendar_reschedule` after its workspace/calendar, membership, active product, and selected row locks and after proposal validation. The guard operates on all proposals at once, before the first activity or audit write. Calendar apply changes activity finishes and planning calendar versions. It does not change starts. The guard checks outgoing links from changed activities and from stages whose effective finish changes. A derived stage's projected finish is the maximum across all active children, using proposed finishes for selected children and stored finishes for the rest. D065 explicit stages retain their stored boundaries, including a missing explicit boundary. The existing D065 interval helper supplies the saved successor start.

Both old and projected dependency bounds use the same authoritative workspace calendar and the first-working-day helper from `0038`. An unchanged or improved bound can proceed. A stricter bound blocks when the successor starts before it. An affected link whose proposed bound exceeds the supported calendar range also blocks. A graph with no edges takes a fast path. The existing validation, audited writes, grouping and rollback stay inside the same SQL call. The migration also makes expected-version and saved-plan comparisons null-safe and rejects a missing proposed finish. This closes the prior SQL null comparison gap for callers of the permitted routine.

The existing apply API returns `409 dependency_conflict` with the first blocking dependency in stable edge-ID order, typed predecessor and successor IDs, a reason, and old and proposed boundaries. The Worker uses the Phase 4 boundary assessment to validate those details. The rejected response contains no operation receipt, and the Worker makes no subset retry. The guard and underlying audited primitive remain inaccessible to the direct Worker role. The ordinary apply function remains its only entry point for this operation.

## Verification and rollout

`0039` depends on unapplied migrations `0036`–`0038`, including the private interval and calendar helpers, and checks that the installed apply body has the reviewed lock and audited write path. The new Worker remains compatible with the old database result contract. Rehearse the ordered migrations and the Worker together before any activation, including the updated `409` contract. Build and source tests alone do not verify PostgreSQL behavior.

The [limited-Worker rollback fixture](../db/verification/phase4b3b1-calendar-apply.sql) requires a separately committed synthetic fixture on an authorized disposable Development child. The second has start `2026-11-09`, finish `2026-11-10` and duration 2. With a current closure on `2026-11-10`–`2026-11-13`, their proposed finishes are `2026-11-09` and `2026-11-16`. Their saved calendar versions must predate the current version, which must be at least 2. Also seed an unlinked working-day activity with start and finish `2026-11-09`, duration 1, and an ID that sorts before the first child. In `Synthetic Phase 4B.3b.1 empty product`, seed one working-day activity with start `2026-11-09`, finish `2026-11-10`, duration 2, and an older saved calendar version. Supply the IDs and calendar version as named `psql` variables.

## Remaining compatibility risks

Calendar reversal still applies its own writes without dependency protection. Child creation, hierarchy changes, deletion, and clone/R00 integration still require their approved checkpoints. Verify apply versus concurrent graph and date mutations, permission boundaries, and exact audit source grouping on the disposable branch before activation. The existing Worker continues to compute proposed end dates from the calendar. This checkpoint validates dependencies on the resulting batch and preserves the existing division of calendar calculation responsibilities.
