# Phase 4B.3c.4 Clone dependencies and R00

Migration `0044` builds on the clone routines installed by `0035` and the dormant dependency storage and write guards in `0036` through `0043`. The clone remains an invoker routine. Its existing workspace and source locks stabilize the source graph across the clone. Vigente, Em estudo and Arquivado sources produce an active Em estudo clone.

The clone captures the source to destination ID maps during stage, stage activity and root activity copies. A scoped executor helper checks active editor membership, same-workspace scope and an Em estudo target created by the actor in the current transaction. It copies the complete graph into that fresh target, with new edge IDs and the original endpoint kinds and directions. It checks endpoint scope, snapshot membership, date and plan equality, and one-to-one mapping. A partial remap raises an exception and the transaction rolls back. It uses the copied rows to write the new R00 and records each edge in the existing Living Schedule operation. The clone pins the generic operation ID while the stage date ledger keeps its individual source operation IDs.

R00 uses the existing dependency array with entries of the form `{id, kind, predecessorId, successorId}`. The immutable trigger stays in place. Direct Worker insertion of nonempty arrays is denied, and imported R00 arrays must be empty. Empty source graphs take the legacy R00 insert path. Ordinary product creation and Excel import use their existing paths, and Excel still ignores `Predecessora`. The Worker receives execution on the scoped clone helper only. General dependency routes and database routines stay dormant.

Supply the four saved source IDs/fingerprints, the four clone product/R00 ID pairs emitted by the Worker, and the missing-remap target ID. This session verifies full source fingerprints, dependency endpoint remapping, clone R00/working graph equality, operation grouping, and rollback of partial edge insertion.

## Checked-in Phase 4B.5 source setup

The clone fixture source setup is split by database authority and audit boundary:

1. `phase4b3c4-clone-seed-owner.sql` creates the isolated workspaces and editor/viewer memberships. It runs the common disposable-child and R00 preflight before any source import, then emits the count and full-row fingerprint of the original six R00 rows.
2. `phase4b3c4-clone-seed-worker-import.sql` runs directly as `jlproject_worker` and calls `import_initial_schedule` four times for a deterministic 7-discipline, 21-stage, 41-activity, 5-target fixture. Each call creates the source R00 through the supported import routine with an empty dependency array. It does not include or infer predecessor data. The deterministic 64-character hash fields satisfy the database import contract; these are synthetic verification inputs, not application idempotency hashes.
3. `phase4b3c4-clone-seed-worker-schedule.sql` uses the public audited stage-date operation to set a complete interval and a partial interval on each source. Its included `phase4b3c4-clone-seed-worker-stage-date.sql` helper commits one stage update per transaction because the legacy stage-date ledger uses a unique operation ID. The same schedule script creates two one-working-day root activities on the Vigente and Arquivado sources through `create_activity_with_working_plan`, grouped as one logical operation per product.
4. `phase4b3c4-clone-seed-owner-dependencies.sql` checks the committed source state and historical R00 baseline, then adds nine edges through `phase4b5-seed-one-dependency.sql`: three activity/stage edges for each linked source, including a root-to-root activity edge on Vigente and Arquivado. Each edge confirmation is its own audited transaction with temporary executor access removed before commit.
5. `phase4b3c4-clone-seed-worker-status.sql` uses `change_product_status` to transition the Em estudo and Arquivado sources after their links exist. Each status change is its own committed Worker transaction. The archived source therefore exercises the public clone path while its two root activities and dependency edge already exist.

Owner edge setup and clone preflight/postflight compare the original six R00 rows by full-row fingerprint while permitting the four supported import-created source R00 rows and four public-clone-created R00 rows. Source fingerprints include product, stages, activities, edges, R00, operation headers, audit events, and schedule cursor. The failed incomplete-remap target remains an expected rollback case with no edge, R00, or audit residue. No clone R00 is fabricated by a seed script.

The owner preflight checks the direct Worker EXECUTE and table privileges, verifies that the Worker cannot read the dependency table, and records source fingerprints before cloning. The Worker fixture tests viewer and cross-workspace denial, normal clone calls for Vigente, Em estudo, Arquivado, and empty sources, direct nonempty R00 denial, and an incomplete endpoint remap. The owner postflight performs privileged graph/R00/audit comparisons. No database permission is broadened for test convenience. Live execution remains pending and is required before considering dependency activation.
