## API contracts

Use the existing `/api/workspaces/:workspaceId/products/:productId` scope. All responses are `no-store`. The authenticated Worker derives the actor from the session. The database rechecks membership and product scope.

| Request | Contract |
| --- | --- |
| `GET …/dependencies` | Active workspace members can read the graph, including archived products. Return the typed edges in stable order, product status and schedule cursor. Resolve endpoint names from authorized schedule data. |
| `POST …/dependencies/preview` | Active editors and admins submit one Phase 4A edit, plus the expected schedule version and the edited row’s version when applicable. Return `ready`, `blocked`, or `unchanged` with the existing domain result. Read the graph, hierarchy, calendar, targets, and schedule cursor from one read-only repeatable-read snapshot. The Worker allocates an ID for a proposed addition and binds it to the preview. Only `ready` receives a short-lived signed confirmation token. |
| `POST …/dependencies/confirm` | Accept the token and mandatory justification. Bind the token to actor, scope, canonical edit, schedule and calendar versions, reviewed result digest, planning-rule version, and operation UUID. Recompute from a fresh snapshot and compare the digest. The Worker sends only its recomputed manifest to the controlled database function. Return the operation ID and committed schedule version. Use the signed operation UUID and the existing unique operation key to recognize an identical retry. A changed justification for a used UUID is a conflict. |

Use `400` for malformed input, `401` for missing authentication, `403` for insufficient role, `404` for an out-of-scope product, and `409` for expired or stale previews, archived writes, or conflicts that require a fresh preview. A preview that is validly formed but has scheduling blockers returns a structured `blocked` result. Enforce request size, graph size, and maximum confirmation batch bounds before computing or writing. Retain the existing origin checks and use a dedicated Worker-only signing secret at activation.

In activation, replace the empty-only check with an object/array shape check that explicitly requires the key, plus the imported-empty invariant. After cloning the hierarchy, copy every live link with a fresh ID, remap through those maps, and serialize the resulting graph into the new R00 before its first insert. A missing map entry aborts the entire clone. Since `clone_product` is currently an invoker, use a narrowly scoped executor helper comparable to the activity clone helpers. Recheck editor membership, same-workspace source and target, source lock, and a target created by that actor in the current transaction. ## Confirmation, permissions, and audit

- Acquire locks in workspace → membership → product → entity order, with stable order inside each entity set. The workspace shared lock serializes confirmation against calendar changes. Bring dependency-sensitive legacy writers onto that protocol before activation. In particular, the existing activity date repository wrapper takes the product lock before an inner function takes the workspace lock, and the stage-date function locks its stage without locking the product. Audit other paths for inversions, including ordinary activity creation and clone writes. After locks, recheck membership, active status, schedule and calendar versions, relevant row versions and exact before values. Compare the proposed link and row identities to the scoped manifest before any write.
- Keep SQL validation focused on graph structure, scoped active entities, D065 writability, exact reviewed inputs, and optimistic checks. Use the Worker recomputation as the authority for calendar and duration math. Bind the final guarded write to the exact row and edge changes that were checked and reject drift before writing. The browser supplies the intent and confirmation, while the database call receives the Worker’s recomputed data. Session settings can carry audit metadata inside the controlled operation. They cannot authorize bypassing dependency validation.
- Set one existing Living Schedule group context with the verified actor, operation UUID, stable operation type, and justification. Use a distinct activity ledger `operation_id` per changed activity and the stage ledger’s independent `event_id` for each stage. Keep specialized before/after values and audit timestamps. Add a generic detail for edge creation/removal and for plan-only changes where applicable. Advance the schedule version once through the existing transaction grouping.
- Complete exact links after all audited mutations in a private executor routine. The installed specialized link triggers run immediately and can see no group header for the first date-only change. The generic linking trigger’s group-ID match alone cannot find a separately keyed activity event. Match activity ledger ID or stage event ID together with product, entity and resulting version, then insert the exact source connection and verify its presence before returning. Keep the unified history projection and paginate complete operation groups. An audit mismatch or write failure aborts the entire transaction. The activity ledger primary key can remain intact.
- Review grants on every existing callable writer. Retain Worker execution only on public guarded entry points for date/graph changes, and keep internal unchecked helpers private. The current invoker importer and manual create route both use direct activity insertion. Before enabling links, route manual creation through a guarded executor call and give the importer a narrow insertion helper restricted to a fresh, authorized import product in the same transaction. Then remove the Worker’s direct activity insert grants. This leaves ordinary inserts and boundary-neutral additions working while closing the linked derived-stage bypass. Test the gate with the actual Worker role, including attempts to supply session settings directly. Enable graph mutations only after all the guards are in place.

## Write-path compatibility

Evaluate only touched links and stages whose D065 effective boundaries can change. For legacy batches and structural writes, validate their projected final snapshot using the same D065 boundary and first-working-day rules. Compare it to the saved state before allowing the existing operation. This keeps a pre-existing conflict elsewhere in the product from blocking ordinary editing. Apply a no-link fast path in the old writers. Existing fixed targets, notes, colors, and order-only edits do not change constraints. A target edit can invalidate a reviewed preview via its schedule version because the warnings may differ.

| Write path | Compatibility before activation |
| --- | --- |
| Root or stage-based activity dates and working plans | For linked activity endpoints or changes to the effective boundary of a linked derived parent, run the Phase 4A preview. Existing direct-only saves can still succeed with their existing justification. If a cascade is needed, return a preview-required conflict and use the explicit confirmation flow. Preserve plan-only and unrelated edits. |
| Stage date edits and date-bearing stage creation | Recompute D065 before and after. Clearing both fields can restore derived dates. One explicit field uses only the stored boundary. An explicit stage cascade writes only the stage. A newly created empty stage has no existing links. |
| Calendar rescheduling and reversals | Validate the full final batch, including affected derived parent stages. Allow the existing transaction if it creates or worsens no violation. Otherwise return a conflict before writes or audit. Calendar configuration alone updates calendar state and can reveal standing conflicts. It never moves schedule dates. |
| Activity, stage or discipline deletion | Expand the active deletion subtree in the locked transaction. Require explicit removal of incident links before deletion and report them in the deletion preview. Validate the remaining links when a deleted child would change a surviving derived parent’s start or finish. Keep the existing fingerprint and rollback semantics. |
| Hierarchy moves | Preserve edges by stable ID. Check both parents when an activity moves into, out of, or between stages and can affect a linked derived interval. Moving a stage between disciplines preserves its children and links. Preserve reorder-only behavior. |
| Manual or working-day child creation | Check the proposed derived interval for a linked parent when dates are supplied. Use the guarded path if it would change a relevant boundary. Root creation, undated creation, and additions with no relevant effect keep their existing behavior. |
| Product status | Archive preserves links and exposes the graph read-only. Reactivation preserves dates and links as saved and can expose standing conflicts. Serialize status changes with confirmations. |
| Clone and import | Clone hierarchy, remapped graph and new R00 in one transaction. Import creates a fresh product and an empty graph. Replay or import failure cannot attach links to an existing product. |
