# Phase 4B.5 PostgreSQL integration execution order

This runbook orders the approved 0036-0044 migration chain and its existing PostgreSQL fixtures. It is preparation only: it does not authorize a branch, migration, database write, route activation, or Production access.

## Before creating a child

1. Use `db/verification/phase4b1-development-catalog.sql` as `neondb_owner` against official Development in a read-only transaction. Confirm the expected baseline, no dependency table, and the reviewed source functions.
2. Confirm migrations 0036-0044 are absent and verify every approved migration checksum. Stop if either check differs.
3. Before creating a child, confirm a native `psql` executable and version, then run temporary read-only `-f` probes through the intended Neon CLI invocation: one must verify `-v` expansion, `\i`, `\if`, and `\gset` with exit 0; a second deliberate SQL error with `ON_ERROR_STOP=1` must exit nonzero. Confirm the CLI did not print its embedded psql fallback message. Remove the temporary probes. Do not create a branch unless both modes behave as expected.
4. Only after separate rehearsal authorization, create and verify an expiring Development child. Record its branch ID and expiry. Every command below must target that child.
5. Before any migration or fixture membership write, use the checked-in Auth gate below. It submits one branch-scoped `POST https://console.neon.tech/api/v2/projects/{project_id}/branches/{branch_id}/auth/users` per role with the deterministic emails `jlproject-phase4b5-admin-<branch-id>@example.invalid` and `jlproject-phase4b5-viewer-<branch-id>@example.invalid`. Require both documented HTTP 201 responses, valid distinct provider UUIDs and an exact match to both child Auth rows. Keep the approved Neon credential in the CLI store or process environment. Do not insert directly into `neon_auth`, reuse a user from a business membership query, or fabricate a JWT. If either creation or verification fails, stop and discard the verified child. Never retry a possibly completed create. [Neon Auth: Create new auth user](https://neon.com/docs/reference/api/auth/create-branch-neon-auth-new-user)
6. Provision synthetic fixture workspaces, memberships, products, stages, activities, dependencies, calendar history, and IDs in committed setup transactions before their corresponding rollback-only test. The owner actor seed assigns the provider-created admin UUID the `admin` membership and the distinct viewer UUID the `viewer` membership; the clone fixture also uses that admin identity for its editor-authorized operations. Do not use Development business rows. Keep different fixture families in separate workspaces unless a fixture explicitly tests a shared workspace calendar.

### Synthetic Auth gate

Use the reviewed Neon CLI executable and the native psql environment with TLS verification. Create the expiring child in step 4 with a `phase4b5-rehearsal-` name. After verifying its exact branch ID, run the gate once and keep the returned object in memory:

```powershell
$auth = & 'db/verification/phase4b5-provision-auth.ps1' -NeonCli $neonCli -BranchId $verifiedChild
```

The gate independently verifies the project, Development parent, child name, expiry, readiness and non-default status. The CLI's `api -i --output json` response includes a textual status and a separate JSON body. JSON mode does not put the status in the body. The gate accepts one complete status line, such as `HTTP 201` or `HTTP/2 201`, at the start of the response and rejects missing, malformed, duplicate or contradictory status evidence. Both process exit 0 and the exact status 201 are required. Each body must supply a nonzero provider UUID. An email in the body must match the expected value. The documented ID-only response is valid, with the exact email always verified against the child Auth row.

The gate keeps raw API output and diagnostics private. It emits `AdminUserId` and `ViewerUserId` only after both create responses pass and the existing `phase4b5-seed-auth-identities-owner.sql` succeeds via the checked-in runner in a separate read-only owner session. A row's existence alone cannot clear the gate. Continue only with the returned pair. The later seed includes still repeat the database check before membership writes.

Pass `-v phase4b5_disposable_child_verified=true` to every seed script. Pass `-v phase4b5_branch_id=<verified-child-branch-id> -v phase4b5_admin_user_id=<Auth-response-UUID> -v phase4b5_viewer_user_id=<Auth-response-UUID>` to the 0041–0044 owner seeds. Pass those values to the same psql process that opens the owner seed with `-f`; native psql processes its `\i` includes in that session, preserving the variables. The shared owner preflight validates the branch ID, both UUIDs, distinct identities, and exact UUID/email pairs against `neon_auth."user"` in a read-only transaction before the fixture write transaction. This is an operator assertion after verifying the child ID; it is not a branch-discovery check. Direct Worker scripts must connect as `jlproject_worker` and use the active synthetic actor IDs printed by the owner setup. Do not use `SET ROLE` or add privileges for fixture convenience.

The reproduced environment used Neon CLI 9.7.2. No native `psql` executable was on `PATH`, so `npx neon@latest psql` used its embedded TypeScript psql implementation. A read-only probe confirmed that `-v` values are present in both `-c` and `-f` modes; the defect is conditional meta-command handling in embedded `-f`: it executed both sides of a `\if`/`\else`, and `\quit 3` returned process status 0. A second probe showed that embedded `-f` does not process `\i`: it sent the include command to SQL and returned `\i: syntax error at or near "\\"`. The shared disposable-child and identity preflights therefore use real SQL exceptions and `ON_ERROR_STOP=1`, not conditional/quit control flow. The identity preflight uses a read-only transaction. A missing psql variable causes SQL parsing to fail with a non-zero process status under `ON_ERROR_STOP=1`; malformed inputs and identity mismatches raise explicit SQLSTATE errors. Do not replace these checks with `\echo`, `\if`, or `\quit` guards.

## Permission checkpoints

The 0036 and complete-chain checks are intentionally different:

- Immediately after 0036, both application roles have no privilege on `product_schedule_dependencies`; this is exactly what `phase4b1-storage-postflight.sql` asserts.
- Starting at 0037, `jlproject_date_executor` intentionally has `SELECT`, `INSERT`, and `DELETE` on the edge table for its private controlled routines. This grant remains part of the final state. The Worker still has no direct table privilege and no execution permission for private graph read/confirm routines.
- Migration 0044 grants the Worker `EXECUTE` only on the clone helper needed by the existing clone path. It does not grant dependency-table reads or general graph mutation. The executor's temporary `CREATE` on `public`, owner SET membership, and R00 trigger privilege are removed by migration cleanup; the R00 trigger privilege is also revoked by 0044.
- Check the function-specific grants after each migration using its postflight. At the end, require Worker execution for the public schedule writers and clone helper, Worker denial for private dependency helpers, and no Worker membership in `jlproject_date_executor`.

Do not treat a permission delta explicitly introduced by 0037 or 0044 as a failure. Do not weaken any assertion to accommodate it.

## Setup script boundaries and remaining prerequisite

Every owner setup includes `phase4b5-seed-safety-owner.sql` and runs in the same psql session through `phase4b5-seed-r00-postflight-owner.sql`, except the 0044 clone source seeder, which deliberately creates four source R00 rows through the Worker import workflow. The shared `phase4b5-seed-one-dependency.sql` confirms exactly one typed edge per transaction, verifies the edge and endpoint IDs, records its audit event, and removes temporary executor membership before commit.

Before running any 0041–0044 owner seed, run the shared `phase4b5-seed-auth-identities-owner.sql` include in that seed's owner session by passing the child branch ID and both UUIDs returned by the branch-specific Neon Auth endpoint. Each fixture then creates only its own synthetic workspace memberships: the provider admin ID is assigned `admin` and the distinct provider viewer ID is assigned `viewer`; the clone's other workspace assigns the admin ID `editor` for the cross-workspace case.
