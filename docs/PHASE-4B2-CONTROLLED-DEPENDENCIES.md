# Phase 4B.2 — Controlled dependency operations

**Status** — Backend implementation prepared. Routes and Worker database execution are closed. Migration execution and activation require separate approvals.

## Prepared contracts

- `GET …/dependencies` scopes the graph and cursor to an active workspace membership. Viewers can read archived graphs. The database reader independently checks membership and returns the graph in stable order.
- `POST …/dependencies/preview` requires an active editor or admin and the expected schedule version. An explicit activity or stage edit also requires its row version. An add supplies two typed IDs. A removal supplies the edge ID. The Worker assigns new edge IDs and addresses endpoint scope through the URL. The Phase 4A engine returns a structured preview. A ready preview includes a Worker-signed token that expires after five minutes. The duration is provisional pending activation review. The token binds actor, workspace, product, rules version, intent, database fingerprint, calendar and schedule versions, and a digest of the reviewed result.
- `POST …/dependencies/confirm` accepts the signed token and justification. It rechecks access, reads a consistent snapshot, recalculates with Phase 4A, and submits exactly one database statement containing the recomputed writes. An already committed operation with the same token and justification can be replayed until token expiry. A different justification is a conflict. The token uses a dedicated Worker-only `DEPENDENCY_PREVIEW_SIGNING_KEY` binding, which is required only at activation. No secret or environment configuration was added.

The graph and snapshot reader caps edges at 5,000 and caps entities, targets and exceptions individually at 2,000. Confirmation caps changed rows at 50, matching the existing calendar batch ceiling. Reassess the bounds during the isolated activation rehearsal. SQL serves a snapshot from one stable statement and guards it again after locking the workspace, membership, and product. PostgreSQL checks typed, active, scoped endpoints with required D065 boundaries, detects cycles after product serialization, and validates reviewed row versions and before values. The Worker remains the authority for calendar calculations. The database trusts the recomputed manifest from the controlled Worker call, so access to the routine is itself a security boundary.

The atomic write reuses the audited activity and stage writers. One grouped operation carries the actor, justification and operation UUID. Each changed activity gets its own specialized ledger ID and each changed stage retains its separate event ID. The routine verifies exact records and links after the row writers, including when the first date event precedes the generic header. Edge add and remove before/after details use the existing generic history projection. Any unexpected row result, audit mismatch or cursor mismatch aborts the whole operation. The activity ledger primary key is preserved.

## Activation blockers for Phase 4B.3

| Existing writer | Bypass to close |
| --- | --- |
| Activity date and working-plan writes | Existing functions can write linked activity dates or change a derived parent boundary without a dependency check. Preserve ordinary direct-only saves and require a distinct confirmation when a cascade is needed. The current repository wrappers take the product lock before the inner workspace lock. Normalize this order for the guarded path. |
| Explicit stage date writes | The installed stage routine locks a stage without taking the product lock and can change a linked D065 boundary. Move the guard and common lock order ahead of date writes. |
| Calendar apply and reversal | Existing batch procedures can move linked activity finishes or change derived parent boundaries. Validate the whole projected final batch before writing. Calendar configuration should continue to change only calendar state. |
| Activity creation | The Worker currently inserts manual activities directly and uses a separate working-plan creation routine. Either can shift a derived parent’s effective boundary. Guard both cases. Adapt the invoker importer to a narrow fresh-product helper before removing direct Worker inserts. |
| Activity, stage or discipline deletion | Soft deletion can orphan incident edges or change a surviving derived stage’s bounds. Require explicit incident-link removal and validate remaining touched bounds. |
| Hierarchy movement | Activity reparenting can change both derived parents. Guard those transitions and retain reorder-only behavior. Stage reparenting preserves the edge IDs. |
| Cloning and importing | The existing clone still writes an empty dependency array to the new R00 and has no dependency remapping. The activation checkpoint must copy live links and serialize the remapped graph into the new R00 in the same transaction. Preserve Excel’s empty graph. |

Keep the no-link path compatible. The dormant handler has no reference from the deployed Worker router, and migration 0037 grants neither it nor the Worker role a way to call the new functions. This is intentional while the writers above remain callable. Archive/status operations and the workspace calendar lock are also part of the activation concurrency review. Apply no grants or route registration until legacy paths, clone R00 compatibility, and history acceptance are verified together.

## Migration and verification gates

Migration 0037 depends on the unapplied 0036 edge storage, existing executor roles and row writers, calendar version storage, and the D066/D067 source-link tables and history projection. It grants only the existing no-login date executor access to the edge store and the calendar exception columns needed to fingerprint the snapshot. It revokes the temporary migration role grants and leaves application calls closed. No migration was executed.

The focused Worker tests cover the dormant route, authorization, graph rejections, preview scope, stale calendar, graph and row state, concurrent application handling, replay and a failure returned from the single database call. These checks and the SQL source tests do not prove PostgreSQL behavior. The [rollback fixture](../db/verification/phase4b2-confirmation-rollback.sql) is prepared for a verified disposable Development child using real `psql`. The fixture commits only a synthetic seed on the child. Its rolled-back test transactions check database cycle and calendar rejection, rollback after a late failure, exact activity IDs, one cursor advance, replay and first-event linking for a date-only operation. Also rehearse concurrent commits from separate connections, mixed activity/stage audit details, lock contention, permissions and complete grouped history with the real limited Worker before activation. The general R00 change and clone integration remain part of Phase 4B.3.
